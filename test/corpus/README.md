# Deploy corpus

Whole deployments run through the Python oracle, with what came out kept as
goldens. The remaining modules (catalog, deploy, cook, spawn) are ported
against these; the modules already ported (config, inputs, archive, lock) are
compared with the oracle on the same files now.

```
python3 test/corpus/corpus.py record  --corpus synthetic     # rewrite the public goldens
python3 test/corpus/corpus.py check   --corpus synthetic     # oracle against goldens
python3 test/corpus/corpus.py compare --corpus synthetic     # and the ported steps against the oracle
```

`compare` also runs the TS engine (`src/deploy.ts`, `src/cook.ts`, through
`src/engine.ts`) on each whole case, at the root the oracle has just run at,
twice ("The name of a build" below), and holds its record against the oracle's: the role's view, plan, apply, the
tree apply left, the calls to cook and to the service manager, the second
apply, the later release, the release taken back, the install without a
start, the switch between an install without a start and a start in both
directions, a unit verifier that refuses, and the refusals. `--steps-only` leaves the engine out; `--node NODE`
names the Node both parts run on (default: the `node` on the search path).

The calls to cook are held with one known difference: the TS adapter adds two
names to cook's environment, `BUN_INSTALL_CACHE_DIR` and `COOK_PASS_ENV`, the
Bun cache of the build's own (`src/isolation.ts`). Every call of the TS
adapter must have both (`cook_calls` in `corpus.py` fails the run otherwise),
and is then compared without them.

The environment of every engine and adapter the corpus starts is set by the
corpus (`fixture_environment`): `PATH` and `HOME` as they are, `LANG` fixed,
`LC_ALL` and `TMPDIR` not set. The adapter hands cook those five names where
they are set and a record names them, so a golden must not follow the
caller's.

`npm test` runs `compare` on the public cases (`test/unit/corpus.test.js`). `--corpus DIR`
takes any other corpus; `import-layer` builds one from a private deployment
layer, and `import-build` adds a case that replays a real build (below). A
corpus built from a private layer, its goldens and its scratch stay outside
this repository: both commands refuse an output path inside it.

## What a case is and what a golden holds

A case (`cases/<name>/case.json`) is the input of one deployment: the four
layers before merging, the pinned versions, base, root and unit directory, the
role's cook command, the recipe file and the archives. The three public cases
are generated by `synthetic.py` and hold no value of any deployed host.

One golden per case, in the order the engine works:

| Section | What it is |
| --- | --- |
| `config` | the four layers as merged (`public_catalog`, `merge_layers`), the effective configuration, the secret names |
| `inputs` | the operator files the controller would hand over, by digest |
| `role` | the role's own call, `Deployment(check=True)` with the role's cook command: request id, pins, plan. Nothing runs |
| `build_name` | what the engine behind the contract hashes for cook in the name of the build: the oracle's two adapter words and the words after them. A kitchen has one word for the first two ("The name of a build" below) |
| `plan` | contract v1 `plan` through `oracle/shim/kitchen_v1.py`: status and `core`, and that nothing was written |
| `apply` | contract v1 `apply`: status and `core`; every file, link and directory it left, with modes and text; how the adapter called cook; what it asked the service manager |
| `reapply`, `plan_after_apply` | the same request again: nothing changes |
| `rebuild` | a later release of the same deployment (another cook pin): a second build beside the first, the pointer and the unit links moved, the unit restarted. In its tree the ownership manifest is listed by entry, in an order that does not follow the root; its digest is kept |
| `release_back` | the first request again, which is how a release is taken back: no cook run, the first build reused, the pointer moved back |
| `install_only` | the same deployment installed and not started, twice, on a sandbox of its own: the staging marker, no enable links, no restart, then nothing to do. Through the engine's class with no verifier (`analyze_command=[]`); the three sections below go through the contract, with a verifier |
| `activation_switch` | the deployment through the contract with a unit verifier found, step by step on a sandbox of its own: installed and not started, the same again, `plan` and `apply` with `activation: start` (no cook run, the enable links, a restart, the marker gone), the same again, `install_only` asked while the unit runs (`plan` says a change, `apply` refuses with `E_UNIT_ACTIVE` and changes nothing), then with the unit stopped behind the engine's back (the links taken away, the marker back, no start or stop), and the same again. Each step holds status and `core`, what it changed and removed, and its calls to the service manager, to cook and to the verifier |
| `activation_switch_unit_without_install_section` | the same steps with a unit that has no `[Install]` section, so that no link differs between the two activations and the engine's marker `state/activation` alone makes the switch a change. Cook is the stand-in here in every case, also in one that replays a build: a kept build's unit is not rewritten |
| `unit_verifier_refuses` | a first install without a start where the verifier exits 7: `E_UNIT_VERIFY` in phase `activate`, the pointer, the unit and its drop-in taken back, the build kept |
| `replayed_build` | only in a case that replays a build: whether the case gives that build's request and name, and which of its files the engine and the adapter left byte for byte |
| `ported` | every call of this deployment that has a TS port, with the oracle's outcome |
| `refusals` | the same deployment with one thing wrong, as met in practice: a recipe or an archive that is not the bytes its pin names, no secrets file, a server command that is not installed |

`core` is the differential surface of the contract (`CONTRACT.md` 2.2). A port
of deploy and cook is right on a case when it produces this `plan` and `apply`
and leaves this tree.

## How the TS engine is run on a case

`ts_driver.mjs` takes the place of the oracle's in-process call. The files are
laid out by the same code, and the record is put together the same way. Two
seams stand around the engine, the same two that stand around the oracle:

- **The host** (`src/io/host.ts`). The oracle's `host_model` replaces
  `Path.lstat` and `pwd.getpwuid`; the TS engine takes a `Host` and asks it
  wherever the oracle calls those. The driver's model answers as `host_model`
  does.
- **The adapter.** The oracle's shim names the cook command
  `[python, oracle/scripts/cook-adapter.py, ...]`, and corpus.py starts
  `adapter_seam.py` in its place. The driver starts `adapter_seam.mjs`, which
  is `src/cook.ts` with `verify_cook` recorded instead of performed.

So what is compared is everything the TS engine and the TS adapter decide and
write. What is not: `verify_cook` itself and the adapter's own entry script.
The lock a real cook writes is compared in the cases that replay a build, and
only there.

## The name of a build

The two engines do not name a build alike, on purpose (ruling D5 in
`test/port-rulings.golden`). Both hash the request and what stands for cook.
The oracle's shim hashes its cook command, which begins with the interpreter
and the path of the adapter script. A kitchen hashes one word in the place of
those two, the name of its adapter contract (`ADAPTER_CONTRACT` in
`src/cook.ts`), so that the name does not follow where Node or kitchen are
installed. The words after them are the same.

A golden shows the oracle's side in `build_name`: its two adapter words, the
words after them, and that the name is what `{REQUEST}` stands for. `compare`
then runs the TS engine twice on each case:

- **With the oracle's name.** The driver hands the engine the shim's two
  words (`EngineOptions.identity`, which nothing but this run may use). The
  record must be the oracle's as text: every path, byte and digest.
- **With its own name.** Nothing is handed in. The harness works the name out
  with the oracle's formula over the oracle's request, with the contract word
  in the place of the shim's two, and looks for the build there; an engine
  that hashed anything else leaves another tree. `build_name` is held apart
  (two words against one, the same words after them, two different names).
  Everything else must be the oracle's record but for digests, and a digest
  may differ only as one that follows from the name: the same oracle digest
  against the same engine digest wherever it stands. The line of a case says
  how many there are.

Then `compare` shows what the name means for an agent, on a sandbox of its
own (`taking_over`):

1. The role's own apply through the Python engine, with the role's cook
   command: the build a deployed agent runs today.
2. A kitchen on that root. Its name for the build is another one; `plan` says
   a build is to be made and writes nothing; `apply` is one cook run, started
   with this Node and the adapter of this install, and one restart, and
   leaves the role's build in place; a second `apply` changes nothing.
3. The same engine from another Node path (a second name of the binary, or a
   copy) and another install location (a copy of `dist` and of the drivers):
   the same contract name, other paths; `plan` and `apply` change nothing: no
   cook run, no restart. A later release from there is one cook run, started
   with that Node and that install, and the same release from the first
   place again changes nothing.

So taking an agent over costs one build and one restart, once, and a move or
an upgrade of Node or of kitchen costs none after that.

A deployment that is installed and not started (`activation: install_only`)
has nothing to restart: there the new build is one cook run and no restart,
and the check also requires that nothing of it is started or enabled.

### The adapter's output under the name of its contract

```
python3 test/corpus/adapter_contract.py check  [--node NODE]
python3 test/corpus/adapter_contract.py record [--node NODE] [--replace]
```

Since the number in the contract name is all that tells the builds of two
adapters apart, it has to be raised when the adapter puts something else into
a build. `check` starts the TS adapter by itself on each public case, as the
engine starts it, and holds what it leaves against
`adapter-contract/<name>.golden`: status, output, how cook was called, and
every file with its mode and text (the recipe written or staged, the layout,
the framework record, the lock after post-processing). `npm test` runs it
(`test/unit/adapter-contract.test.js`), with three changed adapters that it
must fail on.

The present name is `kitchen-cook-adapter/2` (ruling D6). Its record holds
the environment names of each cook call as the adapter hands them, with
`BUN_INSTALL_CACHE_DIR` and `COOK_PASS_ENV`: an empty Bun cache of the
build's own is part of the contract, because it can change which package
versions an install resolves. The record of `/1` left those two names out,
on a ground a review showed false; it stays as it was made and nothing checks
it. No public case has a source repository at a local path, so no record
shows Git's configuration names; `test/unit/test_takeover.py` and
`test/unit/isolation.test.js` hold those, with a real Git.

When it fails because the adapter changed: raise the number in `src/cook.ts`,
build, and `record`; the new name gets a record of its own, the old record
stays, and every agent is built anew once. `record` refuses to rewrite a
record under a name for a change of the adapter. The cases and stand-ins can
change the output too; the record keeps their digests, `check` fails when
they are stale, and `record --replace` rewrites only then. The check sees
what the three public cases exercise and nothing beyond.

## A case that replays a real build

```
python3 test/corpus/corpus.py import-build --corpus DIR --base CASE --name NAME --build COPY [--cooked LOCK]
```

`COPY` holds the files of one build as a deployed host has them: the lock,
`deployment.json`, `cook-recipe.json`, the two layout files, the launcher, the
unit and `.prepared`. `CASE` is the case with the deploy inputs the build was
made from. The command refuses unless the two belong together: the recipe is
the one the layer pins, the launcher and the unit are the ones the lock names,
and the engine's request for `CASE`, with the committed recipe pin and the
role's cook command, is the copy's `deployment.json` and gives the copy's
request id. The new case is `CASE` with the real recipe and with `cook_build`.

In such a case `replay_cook.py` stands where `stand_in_cook.py` does. It
writes the lock, the launcher and the unit of the real build, carried to the
sandbox: paths under the sandbox root, the request id of the run in place of
the real one, and the digests of the three files whose bytes that changes. It
takes out the provenance the adapter adds, since the adapter under test has to
add it, and it refuses a call the real build could not have come from (the
unit name, the host repository and commit, Bun, Node, the layout, the recipe,
the archives and their order). Then everything runs as in any other case, on
both engines.

`replayed_build` in the golden says what that shows beyond the two engines
agreeing:

- `identity`: the request id and the digest of `deployment.json`, worked out
  from the case with nothing moved. `is_the_replayed_build` is true when both
  are the real build's. This is the harness's own formula on both sides
  (`request_of` in `corpus.py`, op `identity` in `ts_driver.mjs`), made of
  each engine's `resolve_pins` and `canonical`; no `Deployment` is asked. It
  shows that the case is the input of the kept build. That each engine itself
  names a build so is in `role`, which holds `Deployment.request_id`.
- `files`: each file of the copy, carried the same way, against what `apply`
  left. The launcher and the unit are equal by construction. The request, the
  staged recipe, the layout, the marker and the lock after the adapter's
  post-processing were written by the engine and its adapter.

The lock as cook wrote it. A copy holds the lock after the adapter rewrote
it, sorted, so by itself it does not say in which order cook wrote the keys,
and the replay then writes the lock sorted. `--cooked LOCK` adds the lock as
cook left it, taken before the adapter read it (`scripts/rehearse/cook-keep`
keeps it during a rehearsal). `import-build` refuses unless it says what the
copy's lock says without the provenance. The replay then writes those bytes,
carried as text: cook's key order, indentation and final newline. Both
adapters read that and must leave the copy's lock, byte for byte.

Limits. The application, the engines and the per-request configuration
directory are not in a copy and are not made up. The snapshots are copied from
the archives of the case after their size and digest matched the lock. Cook
itself does not run in the corpus; a rehearsal runs it (below).

The public case `example-replay` is `example` with a made-up build in that
shape: absolute launcher and unit paths, engine records, a checkout path,
snapshots named by digest, an output outside the build, modes 0700 and 0600, a
credential name nobody declared, and a lock in the key order cook writes.

## A rehearsal: the engine and a real cook on a real account

```
node scripts/rehearse.mjs check|apply|verify --input <absolute rehearsal.json>
```

`scripts/rehearse.mjs` runs contract v1 `plan` and `apply` for one deployment
that is installed and never started (`activation: install_only`), as the
account that owns it, with the real adapter, the real `verify_cook` and a real
cook. Nothing stands in. It is not the operational CLI (phase 7).

- It logs every step as one JSON line and keeps the receipts, one file per
  call of the engine (`<NNN>-<mode>-<command>.receipt.json`, numbered on
  across runs), so a later run never writes over an earlier receipt.
- It refuses to run as root, for another account or home, with any activation
  but `install_only`, or without the user manager's runtime directory.
- `scripts/rehearse/systemctl-readonly` stands in front of the service manager
  and passes `is-active`, `show` and `daemon-reload` only.
- The engine may start three things: its adapter, that reload, and
  `systemd-analyze --user verify`.
- `scripts/rehearse/cook-keep` is named as the cook runtime. It runs Bun with
  the adapter's arguments unchanged and keeps what cook printed and the lock
  as cook wrote it.
- A secrets file is written only where none is, from a template of
  placeholders under the declared names.
- After `apply` it copies the build's small files in the layout `import-build`
  takes, so the build comes back as a case with `--build` and `--cooked`.

The input (`connectome.kitchen-rehearsal/v1`) holds the contract request
without `systemctl`, the service manager's path, the secrets template, the
pinned input files with their digests, and the home and build name the
rehearsal was prepared for. The runner refuses when the engine names the build
otherwise: an input is then not what the rehearsal was prepared with. Where
the bundle and Node are no longer matters to the name (ruling D5).
`test/unit/test_rehearse.py` runs it on the public `example` case behind the
corpus seams (a modelled host, a stand-in cook, the fake service manager).

## A takeover: a running deployment of the role, in two steps

```
node scripts/takeover.mjs check|prepare|verify|start --input <absolute takeover.json>
```

`scripts/takeover.mjs` runs contract v1 `plan` and `apply` for one deployment
that the role made and that is running (`activation: start`), as the account
that owns it, with the real adapter and a real cook. It is not the operational
CLI either. The build and the restart are two steps, so that two operators can
run them:

- `prepare` is `apply` with `phase: prepare`. Cook makes the new build beside
  the running one; the engine adds the build directory and one entry of
  `state/ownership.json`. The pointer, the unit, its drop-in, the enable link
  and the secrets are not touched, and the runner fails if any of them, or the
  unit's process, is not what it was before the step.
- No file of a build that was there is touched either. Bun links package
  files from its cache and sets modes on the linked inodes, so the adapter
  gives it a cache of the new build's own for the one cook run
  (`src/isolation.ts`) and refuses a build that shares a file with another
  build. Git links the objects of a repository at a local path; for one the
  recipe names, the adapter has Git take it over its transport.
- The runner measures it. Before and after a step it takes, of each build it
  measures, the build directory itself and every entry under it (type, mode,
  owner, group, size, link count, inode, modification and status change
  time, a link's target; no contents). The builds measured are all that were
  under `builds` before the step, but for the requested build in `prepare`
  and `start`, which write it; `verify` writes no build and measures the
  requested one too, also when it is the one that runs.
  `untouched_by_this_run` is true only if all of that is as it was, with the
  pointer, the links and the process; false if something changed; and null
  if nothing was seen to change and something of it could not be read: an
  entry of a build, the unit file or a drop-in file, or a property the
  service manager did not answer for: its `show` failed, or ended well
  without the number that the main process id and the restart count always
  are (0 is a number; a time stamp that is not set is empty and answered).
  Two equal "unreadable" marks, or two empty answers, are not an unchanged
  deployment. `prepare` and `verify`
  end with status 3 on false and on null, and the log names what was not
  read (`could_not_be_read`, and `first_not_read` of each build).
- The log line says what it covers: `builds_measured`,
  `requested_build_measured`, `measurement_complete`, `measured` and
  `not_measured`. Not measured, and said so there: file contents, access
  times, what a symbolic link names, the requested build where the step
  writes it, what could not be read, the directory `builds` itself and the
  rest of the root beside the pointer, the agent's state directory, the
  account's own Bun cache, a change that was put back between the two
  moments, and who made a change. It is two looks at the file system, not a
  watch and not a sandbox: a change is seen after it was made.
- `start` is `apply` with both phases on a prepared build: the environment
  file, the pointer, the links, one `daemon-reload`, one `restart`, health.
  It refuses a build that is not prepared, so it never runs cook.
- `activation: install_only` is not a first step here: the engine refuses it
  while the unit is active (`E_UNIT_ACTIVE`), and the runner refuses any
  activation but `start`.
- `scripts/takeover/systemctl-guard` stands in front of the service manager.
  In `check`, `prepare` and `verify` it passes `is-active` and `show` only; in
  `start` also `daemon-reload` and `restart` of the deployment's one unit.
- `verify` reads the secrets file in place and says, by name and yes or no,
  whether every declared name is there and whether `start` would write the
  environment file the running build has. No value, length or digest of a
  secret is logged.
- The recipe is read where the input says its bytes are (the running build's
  staged copy will do) and held against the pin of the configuration, so the
  configured path need not be readable by the account.

The input (`connectome.kitchen-takeover/v1`) holds the contract request
without `systemctl`, the service manager's path, the pinned input files, the
recipe's source, and the home, the account, the name of the running build and
the name of the new one. `test/unit/test_takeover.py` runs the four modes on
the public `example` case after the role's own apply through the Python
engine, behind the corpus seams, and a `start` whose restart fails: the engine
takes it back to the running build.

A first install is the same runner with `live_build: null` in the input:
nothing is deployed. The runner then holds, in place of an engine's root and
a pointer that names the running build, that `builds` has no build but the
requested one, that `current` is not there (in `verify` and `start` it may
name the new build), and that the account has no unit link, enable link or
drop-in directory of this deployment. `prepare` makes the root and the build;
`start` installs and starts the unit through the guard's mode `first-start`,
which passes what `start` passes and `stop` of this one unit. The engine
takes a failed first start back with that `stop`; refused, its take-back
fails and leaves the unit link, the enable link and the drop-in with a
failed unit. `test/unit/test_takeover.py` runs the four modes on a sandbox
where nothing is deployed, a first start whose restart fails (nothing is
left installed, and the next start succeeds), and the refusals where a
build, a pointer or a unit is there.

## What a golden does not show

These are stand-ins, and a golden says so under `engine`:

- **Cook is not run.** `stand_in_cook.py` takes the place of the runtime the
  adapter starts. It records its arguments and writes a launcher, a unit and
  a lock in the shape of the oracle's own fixtures. The adapter's side is
  real: the recipe it writes or stages, the layout, the argv, the environment
  names, how it reads the lock back and adds provenance. The lock's content is
  not what the pinned cook writes; a case that replays a build has that.
- **`verify_cook` is recorded, not performed** (`adapter_seam.py`): no sandbox
  holds a checkout with the pinned commit id.
- **The service manager is the oracle's fake** (`oracle/tests/fixtures/systemctl.py`).
  No unit of the host is asked, started or stopped.
- **The unit verifier is a stand-in** (`stand_in_verifier.py`), in the three
  sections that have one. `corpus.py` puts a script named `systemd-analyze`
  in a directory of the sandbox and that directory first on the search path
  of both engines, so each engine finds it by its own lookup. It writes down
  its arguments and answers as the oracle's double does, or with a set exit
  status. The host's `systemd-analyze` is never run, and what a real verifier
  says of a unit is not shown; the rehearsal ran one.
- **Ownership is modelled** (`host_model` in `corpus.py`, the seam of
  `oracle/tests/deploy_fixtures.py` one step further). The engine requires
  root-owned connector trees and safe ancestors; under a sandbox those are the
  caller's files. They are shown to the engine as root's, and the account's
  home as the one under the sandbox. A TS engine run on a case needs the same
  seam: who owns a path and where the account's home is must be injectable.
- **Layers are merged by the oracle's stand-in for Ansible's `combine`** where
  ansible-core is not installed (ruling R6).
- **Secrets are placeholders** under the declared names.

Paths: every absolute path of a case under the top-level directories of the
deployed host is moved under a sandbox root, in the layers and inside the
recipe. A recipe therefore is not byte for byte the file its layer pins, and
its pin in a run is the digest of the moved bytes. Each case is run at two
roots of different length. In a golden the root is `{ROOT:<directory>}`, this
checkout `{KITCHEN}`, the build's request id `{REQUEST}`, and a digest that
differs between the two roots is path-derived and written
`{sha256:path-derived:N}`; every other digest is literal. So a golden does not
depend on where it was recorded, and it does not pin the value of a
path-derived digest: `compare`, which runs oracle and port at the same root,
is what holds those.
